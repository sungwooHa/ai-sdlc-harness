# 하네스 원칙 (Harness Principles)

> 정본. `AGENTS.md` 는 이 네 원칙의 제목만 싣고 여기를 가리킨다. 하네스에 무엇을 더하거나 뺄 때는
> 먼저 이 네 줄에 비추어 본다 — 어느 원칙도 만족시키지 못하는 요소는 넣지 않는다.
> 확정: 2026-09-14. 근거가 되는 구현은 `AGENT_HARNESS.md` 에 있다.

## 1. 규칙만 저장소에, 이력은 PR 에 — Rules in the repo, history on the PR

하네스는 시스템적 제약과 규칙만 담는다: `AGENTS.md`, `.agents/harness.yaml`, 훅, 스킬, `docs/standards`,
승격된 `docs/knowledge`. 변경 하나의 실행 이력(intent · spec · plan · 산출물 · 스크래치)은 소스 트리에
쌓지 않는다. 그것은 각자의 로컬 폴더에서 태어나 PR 본문과 첨부로 팀에 전달되고 거기서 끝난다.
다음 에이전트가 읽어야 할 **사실과 결정**만 knowledge 로 승격한다. 이력은 지식이 아니다.

- 왜: 여러 명이 개발하는 저장소에 변경마다 문서 4~7개와 팀 스크래치가 쌓이면 클론·리뷰·머지 비용을
  전원이 낸다. 에이전트가 실제로 읽는 것은 규칙과 지식이고, 변경 폴더는 이미 "동결 기록"이었다.
- 구현: `docs/changes/*` gitignore(README·템플릿만 추적), `docs/workbench` 폐기, fast guard 의
  `local_only_roots` 거절, `Plan-Ref:` 커밋 트레일러, `pr.md`.

## 2. 지침이 아니라 시스템으로 강제한다 — Enforce with the system, not with prose

산문은 설득하고 훅은 강제한다. 반드시 지켜져야 하는 규칙은 PreToolUse · Stop · pre-commit · CI 중
**가능한 가장 낮은 층**에 둔다. 호스트 중립(husky · CI)이 우선이고, Claude Code 전용 훅은 그
호스트에만 있는 능력(선택형 질문, 도구 페이로드 검사)일 때만 둔다. 사람이 확인해야 하는 규칙은 그
사실을 문서에 명시한다 — "문서에 있으니 지켜진다"는 팬텀을 만들지 않는다.

- 왜: 지침만 있던 규칙은 매번 새 세션이 다시 어겼다(plan 게이트, 산출물 단계, 질문 폭주).
- 구현: 질문 게이트, 이력 경로 거절, Plan-Ref CI 게이트, PR 본문 게이트, 디자인 토큰 게이트,
  보호 경로 가드. 검증은 `pnpm test:harness`.

## 3. 사람이 보는 것은 인지부하를 최소로 — Minimum cognitive load for humans

사람이 읽고 답하는 모든 표면은 가장 적은 주의를 쓰게 설계한다.
질문은 **선택형**, 한 라운드 4개 이하, 문항당 선택지 3~4개, 추천이 첫 번째, 그 단계의 범주만.
설명은 **그림 먼저**, 상자마다 원인→결과 한 줄, 전문용어 없이(eli7).
PR 은 **짧게**: 한 문장 제목 · 그림 · 세 상자 · 볼 곳 3개 · 증거 10줄, 본문 30줄 이내.

- 왜: intent 인터뷰가 번호 질문 열 개를 한 번에 쏟아내 사람들이 인지부하를 호소했다. PR 이 길면
  리뷰어는 읽지 않는다.
- 구현: `question_gate`, 설명서(eli7) 산출물, `pr_body_gate`, `_templates/pr.md`.

## 4. 사실은 에이전트가, 결정은 사람이 — 필요한 단계만 — Facts are the agent's, decisions are the user's; take only the stages you need

저장소나 도구로 알 수 있는 것은 사람에게 묻지 않는다. 결정은 사람의 것이고, 그 단계에 속한
결정만 그 단계에서 묻는다 — "어떻게"는 spec 이 올 때 묻고 그 전엔 추천 답으로 이월한다.
한 문장 diff 에는 폴더도 산출물도 없다. 산출물은 조건(UI 변경 · 여러 앱 · 계약 변경)이 맞을 때만
요구한다. 단, 여러 도메인이나 `packages/*` 계약을 건드린 변경의 검토는 건너뛰지 않는다.

- 왜: 과한 단계와 조건 없는 산출물 요구는 규칙과 실제를 갈라놓고, 갈라진 규칙은 신뢰를 잃는다.
- 구현: 단계별 질문 범주와 이월 자리(열린 질문 → Flagged Concerns → 리스크), `required_when`,
  UI 리뷰 면제(`시각 변경 없음`), plan 게이트 조건.
