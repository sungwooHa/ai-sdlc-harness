# 오래 유지할 결정 — ADR

ADR은 다음 사람이 "왜 이렇게 했지?"를 다시 조사하지 않도록 남기는 짧은 결정 기록입니다.
변경 하나의 intent·spec·plan·pr.md는 변경 폴더에 커밋하고, 여러 작업에 영향을 주는 결정은 여기에 남깁니다.

## 번호

- **0000 = 하네스 결정 기록.** [`0000-harness-decisions.md`](0000-harness-decisions.md) 한 문서를 제자리에서 고칩니다.
  이력은 `git log -p`가 맡습니다. 하네스를 바꾸면 [`PLAYBOOK_MAP.md`](../standards/PLAYBOOK_MAP.md)의 행 ID를 적고 이 문서를 고칩니다.
- **사용자 프로젝트 ADR은 0001부터.** 한 결정에 한 문서를 씁니다. 번호는 재사용하지 않고, 충돌은 머지 전에 정리합니다.

## ADR 계약

`/__PREFIX__-adr` 스킬과 이 문서는 같은 값을 씁니다.

| 항목 | 값 |
|---|---|
| 루트 | `docs/decisions/` |
| 파일명 | `NNNN-<slug>.md` (사용자 ADR은 0001부터, 0000은 건너뜀) |
| 템플릿 | `docs/decisions/_template.md` |
| 머리 필드 | 상태 · 날짜 · 대체함 · 대체됨 |
| 절 | 배경 · 결정 · 검토한 대안 · 결과와 감수한 비용 · 재검토 조건 · 근거 |

상태는 `proposed`(제안), `accepted`(합의), `superseded`(다른 ADR로 대체)입니다. 실제 합의 근거가 없으면
accepted로 쓰지 않고, 아직 없는 PR 주소나 승인자를 만들지 않습니다. 가능하면 한 페이지로 씁니다.

## 언제 남기나

- 시스템 경계, 주요 의존성, 데이터 소유권 등 구조를 정하거나 바꿀 때
- 여러 곳이 따르는 API·데이터 계약, 보안·배포·운영 정책을 정할 때
- 기존 결정을 뒤집거나, 비용 때문에 선택하지 않은 대안을 이후에도 알아야 할 때
- 하네스의 강제·가이드나 사람과 에이전트의 역할을 바꿀 때 → 새 ADR이 아니라 0000을 고칩니다

단순 버그 수정, 문구·스타일 수정, 영향이 국소적인 구현 선택에는 쓰지 않습니다.
결정이 그대로라면 기존 ADR을 참조합니다. 파일 수나 PR 크기만으로 ADR 필요 여부를 판단하지 않습니다.

## 변경과 연결

1. spec·plan에 결정 초안과 대안을 넣고 관련 ADR을 참조합니다.
2. 계획이 승인되면 ADR을 쓰고 변경과 같은 브랜치에 커밋합니다. 결정이 바뀌면 먼저 다시 합의합니다.
3. PR에서 ADR을 링크합니다. 실행 로그는 ADR에 옮기지 않습니다.

형식은 가이드입니다. 훅이 검사하지 않고, 사람이 PR에서 확인합니다.

## 결정을 바꿀 때

새 ADR을 만들고, 이전 문서에는 superseded 상태와 새 문서 링크만 더합니다. 새 문서의 대체함은 이전 ADR,
이전 문서의 대체됨은 새 ADR로 서로 연결합니다. 형식은 `- 대체함: [ADR-0001](0001-example.md)`이고, 해당 없는 쪽은 `없음`입니다.
제안 단계에서는 두 필드를 없음으로 두고 배경에서 대체하려는 결정을 설명합니다.
원래 이유를 새 결정에 맞춰 고쳐 쓰지 않습니다. 오탈자·깨진 링크 수정은 가능합니다.
(0000은 예외입니다: 대체하지 않고 제자리에서 고칩니다.)

## 하네스에서 사용

Claude에서는 `/__PREFIX__-adr`, Codex에서는 `$__PREFIX__-adr`로 요청하거나 "ADR 만들어", "이 결정을 기록해"라고 요청합니다.
예: "파일 저장소를 교체하기로 한 이유와 대안을 ADR로 남겨줘."
