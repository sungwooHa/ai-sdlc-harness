# 스펙: 공통 검진과 실무 평가의 재사용

| 기준 | 관찰 가능한 결과 |
|---|---|
| A1 | Playbook 대응 상태와 호스트별 강제·실행 증거·효과를 구분한다. 과거 pilot과 현재 적용 상태가 구별되고 반복 문제 환류 기준은 정본 하나를 따른다. |
| A2 | doctor가 스킬 역할 중복·누락, adapter 참조/순환, 양호스트 invocation 정책 불일치를 오류로 검출한다. 정상 템플릿과 초기화본은 통과하고 기존 hook·비밀·보호 규칙은 유지된다. |
| A3 | UI adapter가 반복 입력 종료, 입력 기계적 제약, 조건부 필드 보존, 근거 있는 validation, 중단/복구, 저장/재진입의 해당 경계를 고른다. 내부 작업에 UI 검수를 강제하지 않는다. |
| A4 | 실제 과제는 사용자 프롬프트와 외부 채점 기준이 분리되고 source/권한/도구/결과를 기록한다. 실행 실패·산출물 실패·미검증을 성공과 구별하며 원본 보존과 재실행 절차가 있다. |
| A5 | 승인 전 정지, 승인 후 구현, 독립 리뷰, 실제 브라우저·persistence 검증을 구분한다. 연결된 작업으로 기준 유지와 실패 반환을 확인하며 unavailable capability를 성공 처리하지 않는다. |
| A6 | 모델 없이 실행할 결정적 회귀와 fresh-init을 CI에서 재현할 수 있다. 모델 과제는 명시적 실행으로 남겨 자격 증명·예산을 자동으로 요구하지 않는다. README가 실제 배선과 한계를 설명한다. |

실패 원본은 보존한다. 수정 후 새 후보로 해당 실패와 영향 범위를 다시 확인한다.
합성 평가의 브라우저 결과는 그 평가 제품·backend 범위만 증명하며 LUNA 전체 제품이나 실기기 터치를 증명하지 않는다.
네이티브 승인이 불가능한 lane은 승인 전 검사로 기록하고 다른 실행으로 성공률을 보충하지 않는다.
