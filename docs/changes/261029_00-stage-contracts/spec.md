# Spec: 단계별 인계와 실제 완료 증거

> 근거: ./intent.md · 상태: agreed

## Problem Statement

단계별 문서가 있어도 합의와 최종 사용자 결과 사이의 누락을 발견하지 못한다. 기존 승인 범위에서 각 단계의 책임과 인계를 명확히 하고 같은 내용을 반복 확인하는 경로를 정리한다.

## Solution

A1. 그릴링은 목표·정책·제약의 실질 미결정을 다룬다. 저장소 사실과 일상적인 구현·테스트 선택은 에이전트가 해결한다. 이미 합의한 대화에서 intent를 합성할 수 있고 인터뷰가 자동 재시작되지 않는다.
A2. 스펙은 정상·경계·중단·완료·복구의 관찰 가능한 동작과 인수 기준을 가진다. 승인된 결정과 가정·미결정을 구분한다. API 등 외부 계약과 구현 세부를 구분한다.
A3. 계획은 각 인수 기준을 변경 경계·순서·실행 가능한 검증으로 연결한다. 웹은 최종 환경·backend·계정·실패 주입·browser 담당과 runtime 정리를 준비한다. 사용할 수 없는 환경은 미검증으로 남는다.
A4. 구현과 독립 리뷰는 같은 결정·기준·최종 소스에서 판정한다. 실제 위임 실패는 성공 리뷰가 아니며 실패는 그릴링/스펙/계획/구현 중 원인이 있는 단계로 돌아간다.
A5. 버그·리팩터링·문서 전용 작업은 필요한 판단만 수행한다. 기존 산출물/승인 규칙은 유지하고 도구 이름 때문에 Codex가 Claude 전용 호출을 기다리지 않는다.
A6. 공통 평가기는 호출자의 Git 라우팅을 복사본으로 가져오지 않으며, 성공 응답의 인증 오류 인용을 인프라 실패로 오판하지 않는다. 원본 보존·실제 auth 실패·stdin·자식 정리를 회귀검증한다. 지원 Python에서 기존 테스트가 실행된다.
A7. README/설정/운영 문서는 동일한 기능·한계·명령을 안내한다. 구조 검사·동작 평가·전체 native workflow·브라우저 E2E·효과 비교를 구분한다.

## User Stories

1. 운영자는 같은 결정을 반복 설명하지 않고 각 단계의 결과를 다음 작업자에게 넘긴다.
2. 새 작업자는 전체 대화가 없어도 인계받은 결정과 기준으로 구현/검증한다.
3. 검토자는 구현 성공과 미검증 영역을 원자료에 근거해 판단한다.

## Implementation Decisions

기존 adapter와 templates, 표준 문서에 반영한다. vendored body·hook 권한·manifest schema는 유지한다. 새 프로세스 제어기나 모델 선택 정책을 만들지 않는다.

## Testing Decisions

기존 runner 회귀와 fresh-init, 양호스트 도구 차이/승인 전 경계, 단계별 인계의 실제 산출물을 독립 검수한다. 최종 후보와 다른 source의 실행을 구분한다. 엄격한 blind paired 개선 비교와 native 전체 실행이 불가능하면 해당 주장을 남기지 않는다.

## Flagged Concerns

Claude headless 승인 전 세션은 postapproval 전체 흐름 근거가 아니다. 사용자 승인 env/trust를 에이전트가 제조하지 않는다. 운영 인증·물리 터치는 별도 검증이다.

## Out of Scope

intent.md 비범위와 동일.
